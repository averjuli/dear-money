# Design

## Context

Зачем - см. `proposal.md`, требования - `specs/auth/spec.md` и `specs/envelopes/spec.md`.

Что есть сейчас:

- Вход: один логин и scrypt-хеш пароля из `.env` (`AUTH_USERNAME`, `AUTH_PASSWORD_HASH`), самодельная подписанная cookie `dm_session` на 30 дней (`src/server/auth/session.ts`), проверка в `src/proxy.ts` и в `requireUserId()` (`src/server/auth/current-user.ts`). Пользователь создаётся в таблице `users` (`id uuid`, `login text unique`) при первом входе.
- Данные уже привязаны к пользователю: у `wallets`, `envelopes`, `spend_categories`, `incomes`, `pay_days`, `allocations`, `expenses`, `transfers`, `daily_moves` есть `user_id → users.id` с каскадным удалением. Все функции `src/server/queries.ts` и все действия `src/server/actions.ts` принимают или получают `userId` и фильтруют по нему.
- `notFound()` на экранах кошелька и конверта показывает общую страницу 404 Next.js: своих `not-found.tsx` нет.
- Загрузка данных (`src/db/seed.ts`, `seed-cli.ts`) создаёт пользователя по логину, по умолчанию `AUTH_USERNAME`.
- e2e: вход по логину и паролю 38 раз за прогон, база `dear_money_e2e` пересоздаётся не полностью: `truncate users cascade` после миграций.
- В локальной базе один пользователь, все записи его. На сервере пользователь тоже один: и вход, и `dear-money-deploy seed` идут под `AUTH_USERNAME`.
- Better Auth 1.7.x: адаптер Drizzle - отдельный пакет `@better-auth/drizzle-adapter`; токен MagicLink одноразовый (погашается атомарно при первой проверке), срок по умолчанию 5 минут; новая ссылка старые не отменяет; встроенный лимит - по IP (5 запросов за 60 секунд), а не по почте; сессия по умолчанию 7 дней, `updateAge` 1 день; серверные компоненты Next.js не могут ставить cookie.

## Goals / Non-Goals

**Goals:**

- Заменить самодельный вход на Better Auth с MagicLink, не меняя `user_id` в таблицах данных: id пользователя-владельца остаётся тем же, его данные никуда не переезжают.
- Все правила входа (почта, лимит, срок ссылки, «только последняя ссылка») проверяет сервер, на любом пути запроса - и из формы, и в обход неё.
- Одна сборка приложения: куда уходят письма и какой адрес у ссылки, задают переменные окружения.
- Миграция и смена почты владельца проходят одной транзакцией: либо всё, либо ничего.

**Non-Goals:**

- Переписывать запросы к данным: фильтр по `user_id` уже есть, его проверяем и закрываем автотестами, а не строим заново.
- Отдельные экраны «не найдено» для трат, переводов и категорий: спека требует тексты только для кошелька и конверта, остальное по-прежнему отвечает общей 404.
- Проверка доставки на сервере автотестами: письма через Resend проверяются настоящей выкаткой.

## Decisions

### 1. Better Auth поверх существующей таблицы `users`

Better Auth работает с таблицей `users`: модель `user` с `usePlural: true`, id - UUID (`advanced.database.generateId: "uuid"`). В `users` появляются поля пользователя Better Auth: `email` (уникальная, не пустая), `name` (пустая строка, имя не спрашиваем), `email_verified`, `image`, `updated_at`; `login` убирается. Новые таблицы Better Auth: `sessions` (вход на устройстве), `accounts`, `verifications` (ссылки для входа). Схему подсказывает генератор Better Auth (`pnpm dlx auth@latest generate`), в `src/db/schema.ts` она приводится к стилю проекта: `snake_case` в базе, `uuid`, `timestamp with time zone`.

Альтернатива - отдельная таблица пользователей Better Auth и связь с `users`. Отклонена: лишняя таблица и лишнее соответствие, а все внешние ключи данных уже смотрят на `users.id`.

### 2. Почта владельца из `OWNER_EMAIL` в той же транзакции, что и миграция

`src/db/migrate.ts` читает `OWNER_EMAIL`, нормализует (см. решение 3) и до запуска миграций ставит её на соединение настройкой сессии Postgres `dear_money.owner_email`. Миграции Drizzle идут одной транзакцией на этом соединении. Новая миграция:

1. добавляет в `users` колонки пользователя Better Auth, пока `email` может быть пустой;
2. в блоке `DO`: если пользователей нет - ничего не делает (новая база, CI, e2e); если пользователь один - ставит ему `email = current_setting('dear_money.owner_email')`, `email_verified = true`; если почта не задана - `RAISE EXCEPTION` с понятным текстом; если пользователей больше одного - `RAISE EXCEPTION`: чьи это данные, решает человек;
3. делает `email` обязательной и уникальной, убирает `login`, создаёт `sessions`, `accounts`, `verifications`, `sign_in_links`.

Исключение откатывает всю транзакцию: база как до выкатки, `dear-money-deploy` пишет «migrations failed», новый образ не стартует. `user_id` в данных не меняется, поэтому число кошельков, конвертов, категорий, трат и доходов то же. Миграцию Drizzle генерирует по схеме, блок `DO` дописывается в SQL руками.

Альтернатива - отдельный шаг на TypeScript после миграций. Отклонена: между миграцией и шагом `email` пустая и не может быть обязательной, а упавший шаг оставляет базу наполовину переделанной.

Почта не попадает ни в код, ни в миграцию: репозиторий публичный.

### 3. Проверки запроса ссылки - в хуке Better Auth

`hooks.before` Better Auth на путь `/sign-in/magic-link` срабатывает и для формы, и для запроса в обход неё:

- нормализует почту: пробелы по краям убираются, буквы маленькие; дальше Better Auth работает уже с ней;
- неверный адрес → `APIError` `BAD_REQUEST` с кодом `INVALID_EMAIL`;
- лимит превышен → `APIError` `TOO_MANY_REQUESTS` с кодом `TOO_MANY_SIGN_IN_LINKS`.

Правила - чистые функции с тестами Vitest (TDD): `normalizeEmail`, `isValidEmail` в `src/server/auth/email.ts`; `canSendSignInLink(sentAt[], now)` в `src/server/auth/sign-in-limit.ts`. Верный адрес: не длиннее 254 символов, без пробелов, ровно одна `@`, непустая часть до неё, после неё домен с точкой, по краям точки не пусто. `normalizeEmail` используется и в загрузке данных, и в миграционном скрипте.

### 4. Журнал ссылок `sign_in_links`: лимит и «только последняя ссылка»

Своя таблица `sign_in_links`: `id`, `email`, `token_hash` (SHA-256 токена), `created_at`; индекс по `(email, created_at)`. `user_id` в ней нет: запись появляется до того, как пользователь существует, и это служебная таблица входа, как `verifications`, а не данные пользователя.

- Отправка (`sendMagicLink`): запись в журнал → письмо; письмо не ушло - запись удаляется, ошибка идёт дальше. Заодно удаляются записи старше суток.
- Лимит: в хуке из решения 3 - не больше 3 записей для почты за последние 10 минут.
- Только последняя ссылка: `hooks.before` на `/magic-link/verify` ищет запись по хешу токена и сверяет, что она самая новая для своей почты. Нет записи или есть новее → `ctx.redirect("/login/expired")`, токен Better Auth не трогается.
- Срок и одноразовость - сам Better Auth: `expiresIn: 900`, токен гасится при первой проверке, ошибка ведёт на `errorCallbackURL` `/login/expired`. Экран показывает одно и то же для любой ошибки: устарела, использована, отменена, неизвестна.

Альтернатива - при новой ссылке удалять старые строки в `verifications`. Отклонена: зависит от внутреннего формата Better Auth (что лежит в `identifier` и `value`), его меняют от версии к версии.

Встроенный лимит Better Auth по IP остаётся защитой от потока запросов, но ослаблен до 30 запросов в минуту на путях MagicLink: 5 в минуту строже спеки и ломает e2e. Адрес клиента Better Auth берёт из `X-Forwarded-For`, его ставит nginx.

### 5. Вход на устройстве: сессия 30 дней и продление в proxy

Сессии Better Auth: `expiresIn` 30 дней, `updateAge` 1 день. Каждый заход позже чем через сутки после прошлого продления сдвигает срок на 30 дней от этого захода. Каждое устройство - своя строка в `sessions`, поэтому вход с нескольких устройств работает сам.

Серверные компоненты cookie ставить не могут, поэтому продлевает `src/proxy.ts` (в Next.js 16 он работает в Node.js): вызывает `auth.api.getSession({ headers, asResponse: true })`, нет сессии - редирект на `/login`, есть - пропускает запрос и переносит `Set-Cookie` из ответа Better Auth. Иначе срок в базе продлится, а cookie в браузере кончится через 30 дней после входа. Экраны проверяют сессию ещё раз: `requireUserId()` и новый `requireUser()` (id и почта) в `src/server/auth/current-user.ts` через `auth.api.getSession`. Имя `requireUserId()` остаётся, поэтому экраны и действия не меняются.

Альтернатива из документации Better Auth - в proxy проверять только наличие cookie (`getSessionCookie`). Отклонена: cookie не продлевается, вход держался бы 30 дней с входа, а не с последнего захода. Цена решения - один запрос к базе в proxy на каждую страницу.

`matcher` в proxy пропускает без входа `/login` и `/login/expired`, `/api/auth/*`, `/health`, `/install`, манифест и иконки.

### 6. Письма: Nodemailer по SMTP, адрес решают переменные

- `src/server/mail/transport.ts`: `nodemailer.createTransport` из `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`; `secure` при порте 465; без пользователя - без авторизации (Mailpit).
- `src/server/mail/sign-in-email.ts`: чистая функция `signInEmail(url)` → тема, HTML с кнопкой «Войти» и текстовая версия; отправитель - константа `"Dear Money" <noreply@mail.dearmoney.space>`. Тест Vitest проверяет тексты из спеки.
- На компьютере и в CI: Mailpit, SMTP `localhost:1025`, страница и API `http://localhost:8025`. На сервере: SMTP Resend `smtp.resend.com:465`, пользователь `resend`, пароль - ключ API.
- `deploy/compose.yaml` даёт по умолчанию хост, порт и пользователя Resend; в `.env` сервера нужен только ключ (`SMTP_PASSWORD`).

Альтернатива - пакет `resend` или его HTTP API. Отклонена: спека требует Nodemailer, а SMTP оставляет один путь отправки для заглушки и для сервера.

### 7. Адрес приложения и секрет

- Ссылка строится от `BETTER_AUTH_URL`: на компьютере `http://localhost:3000`, в e2e `http://localhost:3100`, на сервере `https://app.dearmoney.space`, задан прямо в `deploy/compose.yaml`: это не секрет.
- Секрет - уже существующий `AUTH_SECRET`: Better Auth берёт его, если нет `BETTER_AUTH_SECRET`. Новой строки с секретом нет, в production без секрета Better Auth не стартует.

### 8. Next.js: обработчик, страница входа, выход

- `src/app/api/auth/[...all]/route.ts` - `toNextJsHandler(auth)`. Плагины: `magicLink(...)`, последним `nextCookies()`, чтобы действия сервера ставили и снимали cookie.
- Действие `requestSignInLink` вызывает `auth.api.signInMagicLink` с `callbackURL: "/"`, `newUserCallbackURL: "/"`, `errorCallbackURL: "/login/expired"`. Ответ: `INVALID_EMAIL` → «Проверьте адрес почты» под полем; `TOO_MANY_SIGN_IN_LINKS` → «Слишком часто, попробуйте через несколько минут»; успех → «Ссылка для входа отправлена на <почта>» с уже нормализованной почтой.
- Поле «Почта»: `type="email"`, `autoComplete="email"`, форма с `noValidate`, чтобы под полем было сообщение сервера, а не подсказка браузера.
- `/login/expired`: «Ссылка устарела, запросите новую» и кнопка на `/login`.
- Действие `logout`: `auth.api.signOut` удаляет только сессию этого устройства → `redirect("/login")`.
- «Настройки»: в карточке первой строкой почта текущего пользователя (обычный текст, не ссылка), дальше «Как установить на iPhone» и «Выйти».

### 9. «Не найден» и пустая главная

- `src/app/wallets/[id]/not-found.tsx` - «Кошелёк не найден» (и для `/wallets/<id>/edit`), `src/app/envelopes/[id]/not-found.tsx` - «Конверт не найден», `src/app/envelopes/new/not-found.tsx` - «Кошелёк не найден» (новый конверт в чужом кошельке). Экран в стиле приложения со ссылкой на главную. Чужая запись и несуществующая выглядят одинаково: экраны уже ищут запись только среди своих.
- Главная без кошельков: вместо «Кошельков пока нет. Создать первый» - ссылка «Создайте первый кошелёк» на `/wallets/new`.
- Проверка «своё только своё»: пройти по всем экранам в `src/app/**/page.tsx` и действиям в `src/server/actions.ts` и убедиться, что каждый вызывает `requireUserId()` и каждый запрос к таблицам данных фильтрует по `user_id`; e2e закрывает прямые ссылки на чужие кошелёк и конверт.

### 10. Загрузка данных по почте

`seedUserData(db, email, data)` нормализует почту, создаёт пользователя (`email_verified = true`, `name = ''`), если его нет, и грузит данные как раньше. `pnpm db:seed <файл> [--email <почта>]`: без `--email` - `OWNER_EMAIL`, нет и её - ошибка с подсказкой. `dear-money-deploy seed` идёт через контейнер приложения, у которого `OWNER_EMAIL` уже есть.

### 11. e2e: Mailpit, вход один раз, время сдвигом в базе

- `e2e/mailpit.ts`: очистить ящик, дождаться последнего письма на адрес, достать из него ссылку и заголовки - через API Mailpit (пути сверить по его Swagger при реализации).
- Проект Playwright `setup` (`e2e/auth.setup.ts`) входит под демо-пользователем `demo@example.test` по ссылке из Mailpit и сохраняет вход в `e2e/.auth/demo.json` (в `.gitignore`). Проекты `iphone` и `computer` зависят от него и берут сохранённый вход; контексты, которые тесты создают сами, получают его явно. Вход перед каждым тестом не годится: 38 входов за прогон упираются в лимит 3 письма за 10 минут.
- `e2e/login.spec.ts` - отдельный проект `login` без сохранённого входа: пользователи A и B, все сценарии из `specs/auth/spec.md`.
- Сроки (16 минут, 10 минут лимита, 30 дней и продление) проверяются на настоящей базе: тест сдвигает назад `created_at` в `sign_in_links`, `expires_at` в `verifications` и `sessions`. Моков нет.
- `e2e/global-setup.ts` удаляет и создаёт `dear_money_e2e` заново: в старой e2e-базе два пользователя по логину, миграция на ней откажется работать. Ещё он очищает Mailpit и грузит демо-данные на `demo@example.test`, а чужие - на `someone-else@example.test`.
- Настройки сервера приложения для e2e - в `e2e/env.ts`: `BETTER_AUTH_URL`, `SMTP_HOST`, `SMTP_PORT`, случайный `AUTH_SECRET`.

### 12. Docker и CI

- `docker-compose.yml`: сервис `mailpit` (`axllent/mailpit`, последняя стабильная версия, сейчас v1.33.1), порты `127.0.0.1:1025` и `127.0.0.1:8025`, `restart: unless-stopped`, логи с ограничением, как у `db`.
- `.github/workflows/ci.yml`, задача Playwright: сервис `mailpit` из того же образа, порты 1025 и 8025. Имена задач не меняются: на них держится защита main.
- `deploy/compose.yaml`: приложению и разовому контейнеру миграций - `OWNER_EMAIL`, `BETTER_AUTH_URL`, `SMTP_*`; `AUTH_SECRET` остаётся обязательным; `AUTH_USERNAME` и `AUTH_PASSWORD_HASH` - необязательными, только для отката на прошлую версию.

### 13. Что уходит

`src/server/auth/password.ts`, `session.ts` и их тесты, `scripts/auth-setup.ts`, скрипт `auth:setup` в `package.json`, предупреждение «Вход ещё не настроен» на странице входа.

### 14. Мелочи, которых нет в спеке

Решены так, пользователь может поменять:

- Кнопка на экране устаревшей ссылки - «Запросить новую ссылку».
- Письмо не ушло (почтовый сервис недоступен) - «Не удалось отправить письмо, попробуйте ещё раз» на странице входа.
- После «Ссылка для входа отправлена на <почта>» форма остаётся на месте: можно запросить ещё раз или ввести другую почту.
- На экранах «Кошелёк не найден» и «Конверт не найден» - ссылка «На главную».

## Risks / Trade-offs

- [Домен Resend не подтверждён к моменту выкатки → на сервере никто, включая владельца, не может войти] → подтвердить домен `mail.dearmoney.space` и проверить ключ до merge; задача в `tasks.md` блокирует merge.
- [Детали Better Auth 1.7 отличаются от документации: `ctx.redirect` в хуке, `Set-Cookie` при продлении в `getSession`, `generateId: "uuid"`] → сверить с установленной версией в самом начале реализации; продление и редиректы проверяет e2e.
- [Проверка сессии в proxy - запрос к базе на каждую страницу] → для одного-двух пользователей незаметно; при росте включить `cookieCache` Better Auth.
- [Два одновременных запроса на одну почту проходят лимит и уходят 4 письма] → принимаем: на лимит в 3 письма это не влияет заметно.
- [За nginx Better Auth видит не тот IP, и лимит по IP общий на всех] → nginx уже ставит `X-Forwarded-For` и `X-Real-IP`; лимит 30 в минуту, общий он не мешает.
- [На сервере больше одного пользователя → миграция откажется] → выкатка остановится до изменений, прежняя версия работает; спросить пользователя, чьи данные.
- [Старая версия не работает с новой базой: колонки `login` больше нет] → откат только вместе с базой из копии; порядок в `README.md`.
- [В e2e тесты пишут в одну базу и один ящик Mailpit] → тесты идут по одному (`workers: 1`), у каждого сценария своя почта, письма ищутся по адресу получателя.

## Migration Plan

До merge, делает человек:

1. Resend: регистрация, домен `mail.dearmoney.space`, записи DNS для него, ключ API.
2. `/opt/dear-money/.env` на сервере: добавить `OWNER_EMAIL` и `SMTP_PASSWORD` (ключ Resend). `AUTH_USERNAME`, `AUTH_PASSWORD_HASH`, `AUTH_SECRET` не удалять: `AUTH_SECRET` нужен новой версии, остальные - для отката.
3. `.env` на компьютере: `OWNER_EMAIL`, `BETTER_AUTH_URL=http://localhost:3000`, `SMTP_HOST=localhost`, `SMTP_PORT=1025`; `docker compose up -d db mailpit`, `pnpm db:migrate`.
4. Пользователь смотрит SQL миграции, которая меняет данные.

Выкатка - как обычно, merge в main: бэкап базы → миграции с `OWNER_EMAIL` → новый образ → smoke `/health`. Упали миграции - работает прежняя версия на прежней базе.

После выкатки: войти на app.dearmoney.space по ссылке на свою почту и сверить кошельки, конверты, траты и доходы с тем, что было.

Откат, вручную: `sudo dear-money-deploy rollback`, затем `sudo dear-money-deploy restore <копия, снятая этой выкаткой>`. Версии совпадут: копия подписана версией до выкатки. Прошлая версия стартует, потому что `deploy/compose.yaml` всё ещё передаёт ей `AUTH_USERNAME` и `AUTH_PASSWORD_HASH`.

Потом, отдельной правкой, когда новая версия проверена: убрать `AUTH_USERNAME` и `AUTH_PASSWORD_HASH` из `deploy/compose.yaml` и из `.env` на сервере.
