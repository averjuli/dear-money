# Design

## Context

- Журнал `daily_moves` уже хранит каждое изменение «на жизнь» от переводов и повседневных трат («как стало − как было»), строка привязана к последнему доходу на момент записи. Строки появляются только после первой раскладки
- Сейчас карточка считает бюджет и «потрачено» только по строкам последнего дохода (`periodBudget`, `periodSpent` в `src/domain/daily.ts`, `loadDailySummary` в `src/server/queries.ts`), а «в день» - по `incomes.next_income_date`
- Таблицы для настроек пользователя пока нет; `users` хранит только логин

## Goals / Non-Goals

**Goals:**
- Остаток на жизнь как накопительная сумма без пересчёта старых данных
- Числа аванса и зарплаты на пользователя, с фильтром по `user_id`
- Ближайшая дата денег и сумма в день - чистые функции в `src/domain/` с тестами по числам из сценариев

**Non-Goals:**
- Не меняются раскладка дохода, половина взноса, остатки конвертов, категории и «Потрачено в <месяце>»
- Вид дохода (зарплата, аванс, другое) не связывается с числами: числа нужны только для «в день»
- Отдельного экрана настроек для чисел нет: они задаются на «Пришли деньги»

## Decisions

### 1. Остаток = все доли доходов + весь журнал

`remaining = Σ incomes.to_daily + Σ daily_moves.amount` по пользователю, без фильтра по доходу. Журнал уже даёт правильные знаки для новых, исправленных и удалённых трат и переводов, а траты до первой раскладки в нём не записаны. Поэтому все сценарии получаются без миграции данных, а уже внесённые суммы сохраняются.

Колонка `daily_moves.income_id` остаётся: она не мешает и пригодится для истории. Код записи в журнал не меняется.

Альтернатива: хранить «остаток на момент дохода» в `incomes`. Отклонено: пришлось бы пересчитывать его при каждой правке старой траты.

### 2. Таблица `pay_days`

Одна строка на пользователя: `user_id` (уникальный, каскад при удалении пользователя), `advance_day` и `salary_day` - `smallint`, могут быть пустыми, проверка `between 1 and 31`. По «Разложить» строка вставляется или обновляется (`on conflict (user_id) do update`) в той же транзакции, что и доход. Строки нет - оба поля пустые.

Альтернатива: колонки в `users`. Отклонено: `users` - это вход, а настройки другого пользователя потом проще держать рядом с остальными данными по `user_id`.

### 3. Колонка `incomes.next_income_date` удаляется

Она больше нигде не читается. Миграция `drop column`; старые даты следующего дохода теряются, на суммы это не влияет.

### 4. Функции в `src/domain/daily.ts`

- `nextPayDate(today, days: (number | null)[]): string | null` - для каждого заданного числа ближайший день строго после сегодня: в этом месяце, если он ещё впереди, иначе в следующем; число больше длины месяца - последний день месяца. Берётся самый ранний; все пусты - `null`
- `dailyRemaining({ toDaily: number[], moves: number[] })` - сумма
- `dailySummary({ remaining, today, payDays })` → `{ remaining, nextPayDate, perDay }`: `perDay = roundToRubles(divRound(remaining, daysUntil(today, nextPayDate)))`, при `nextPayDate = null` - `null`. Дней всегда ≥ 1, потому что дата строго после сегодня. Отрицательный остаток даёт отрицательную сумму в день, строка не прячется
- Удаляются `periodBudget`, `periodSpent` и поля `budget`, `spent`, `daysLeft`. `dailyMove` и `remainingAfterExpense` остаются как есть

Округление остаётся в `money.ts` (`divRound`, `roundToRubles`).

### 5. Экраны

- `income-form.tsx`: вместо поля даты два поля `inputmode="numeric"`, предзаполнены числами из `pay_days`; пустое поле → `null`; проверка 1–31 на клиенте и в `allocateIncome`
- `daily/page.tsx`: текст `InfoTip` - «Это деньги, оставшиеся после распределения по конвертам»; заголовок «Осталось на жизнь до <formatDay(nextPayDate)>» или без даты, сумма, «Пополнить», строка «≈ N ₽ в день», если `perDay` не `null`; `Bar` и «потрачено X из Y» убираются
- `page.tsx` (главная): `Bar` убирается, сумма остаётся. Цвет предупреждения для минуса на экране «Траты» и в подсказках не меняется

## Risks / Trade-offs

- [После выкатки «Осталось на жизнь» сразу вырастет на остатки прошлых периодов] → это и есть новое правило; в описании PR сказать, что цифра поменяется, и как её сверить
- [Удаление колонки необратимо] → в колонке только даты следующего дохода, они не участвуют в суммах; удаление согласовано с пользователем
- [Сегодня считается по часовому поясу сервера `APP_TIME_ZONE`] → так же, как сейчас для дат трат и месяца

## Migration Plan

1. Одна миграция Drizzle: `create table pay_days`, `alter table incomes drop column next_income_date`
2. Выкатка обычным путём: разовый контейнер применяет миграцию, затем стартует новый образ
3. Откат: предыдущий образ читает `next_income_date`, поэтому после миграции он не запустится без возврата колонки. Откат вручную - миграция с `add column next_income_date date` (пустой) и предыдущий образ
