# Design

## Context

- Кошелёк своих денег не хранит: его сумма - сумма остатков его конвертов (`loadWallets` в `src/server/queries.ts`).
- Остаток конверта считается на лету: `envelopeBalance` в `src/domain/envelope.ts` = начальный остаток + строки раскладки (`allocations`) − траты (`expenses` с `envelope_id`). Сохранённых остатков нет.
- «Осталось на жизнь» на главной, на экране «Траты» и в подсказке новой траты - `dailySummary` в `src/domain/daily.ts`: бюджет = `incomes.to_daily` последнего дохода, потрачено = траты без конверта с датой не раньше даты этого дохода (`periodStart`, `loadDailySpent`). Последний доход - `loadLatestIncome`: по дате дохода, потом по времени внесения. До первой раскладки карточки нет.
- Раскладка (`src/domain/allocation.ts`) берёт текущие остатки конвертов из `loadWallets` и по ним решает, кто полный и куда идёт излишек.
- Форма траты (`src/app/expenses/expense-form.tsx`) одна для новой траты и правки. Для конверта подсказка при правке прибавляет старую сумму обратно к остатку. Подсказка «На жизнь останется» есть только у новой траты: страница правки (`src/app/expenses/[id]/page.tsx`) остаток на жизнь не передаёт. Дата - поле `type="date"` с `max = today`.
- Траты меняются только действиями `saveExpense` и `deleteExpense`; загрузка начальных данных (`src/db/seed.ts`) траты и доходы не загружает.
- Удаление конверта и кошелька - настоящее удаление строк; траты и строки раскладки уходят каскадом.
- e2e-сценарии делят одну базу с демо-данными и идут по порядку; к началу новых сценариев главный сценарий уже разложил доход и внёс траты.

## Goals / Non-Goals

**Goals:**

- Перевод - одна запись с двумя сторонами; остатки конвертов по-прежнему считаются на лету.
- Переводы и повседневные траты меняют текущее «на жизнь» по одному правилу: на разницу «как стало − как было», в момент изменения, какой бы ни была дата.
- Раскладка, главная и «Пришли деньги» видят переводы без своих правок: через остатки из `loadWallets` и общий подсчёт «на жизнь».
- Одна форма для нового перевода и правки, как у трат.
- Вся арифметика переводов и «на жизнь» - в `src/domain/`, с тестами на числа из сценариев.
- После миграции цифры на экранах те же, что до неё.

**Non-Goals:**

- Перевод будущей датой, перевод сразу в несколько конвертов.
- Переводы на главной и на экране кошелька (история только у конверта и на «Тратах»).
- Перевод «на жизнь» → «на жизнь» и перевод между пользователями.
- Категории, лимиты и «Потрачено в <месяце>» не меняются: по-прежнему по дате траты, за календарный месяц.
- «На жизнь» как постоянный остаток без периодов - отдельная правка.

## Decisions

### 1. Модель: таблица `transfers`, у каждой стороны «конверт или на жизнь»

```
transfers
  id               uuid pk
  user_id          uuid not null → users (cascade)
  amount           integer not null, > 0        -- копейки
  date             date not null                -- дата из формы
  from_daily       boolean not null default false
  from_envelope_id uuid null → envelopes (on delete set null)
  to_daily         boolean not null default false
  to_envelope_id   uuid null → envelopes (on delete set null)
  created_at       timestamptz not null default now()
```

Проверки в базе:
- `amount > 0`;
- не обе стороны «на жизнь»: `not (from_daily and to_daily)`;
- у стороны «на жизнь» нет конверта: `not from_daily or from_envelope_id is null`, то же для `to`;
- не один и тот же конверт: `from_envelope_id is distinct from to_envelope_id or from_envelope_id is null`.

Индексы: `user_id`, `from_envelope_id`, `to_envelope_id`.

Сторона читается так: `*_daily = true` - «на жизнь»; иначе конверт `*_envelope_id`; если он пустой - конверт удалён. Поэтому флаг нужен отдельно от ссылки: по одной пустой ссылке нельзя отличить «на жизнь» от удалённого конверта.

`on delete set null` вместо каскада: при удалении конверта перевод остаётся у второй стороны, деньги там и остаются (требование «Перевод удалённого конверта»). Удаление кошелька удаляет конверты каскадом, дальше то же самое.

Альтернативы:
- Две строки, расход и приход, в `expenses` и `allocations`. Отклонено: перевод начал бы считаться тратой в категориях и «Потрачено», а строки раскладки привязаны к доходу.
- Одна колонка-вид (`envelope_to_envelope`, `envelope_to_daily`, `daily_to_envelope`). Отклонено: проверки и запросы по сторонам выходят длиннее, чем с двумя флагами.

### 2. Журнал изменений «на жизнь» - таблица `daily_moves`

Каждое сохранение и удаление перевода или траты меняет текущее «на жизнь» на разницу «как стало − как было» - так, будто «на жизнь» - кошелёк, где любое изменение видно сразу. Эта разница записывается строкой журнала в период последнего дохода:

```
daily_moves
  id          uuid pk
  user_id     uuid not null → users (cascade)
  income_id   uuid not null → incomes (cascade)       -- период: последний доход в момент изменения
  source      daily_move_source not null              -- 'transfer' | 'expense'
  transfer_id uuid null → transfers (on delete set null)
  expense_id  uuid null → expenses (on delete set null)
  amount      integer not null, <> 0                  -- копейки со знаком: + в «на жизнь», − из «на жизнь»
  created_at  timestamptz not null default now()
```

Проверки: `amount <> 0`; `source = 'transfer' or transfer_id is null`; `source = 'expense' or expense_id is null`. Индексы: `user_id`, `income_id`, `transfer_id`, `expense_id`.

`source` хранится отдельно от ссылок: после удаления перевода или траты ссылка пустая, а строка всё равно должна знать, куда она идёт - в бюджет или в «потрачено».

Текущий период (последний доход `I`):
- бюджет = `I.to_daily` + сумма строк `source = 'transfer'` с `income_id = I`;
- потрачено = −(сумма строк `source = 'expense'` с `income_id = I`);
- осталось = бюджет − потрачено.

Сумма строки (`dailyMove`, решение 3) = «влияние на «на жизнь» как стало» − «сумма уже записанных строк этого перевода или траты». Влияние: пополнение +сумма, перевод из «на жизнь» −сумма, повседневная трата −сумма, перевод между конвертами и трата из конверта 0, удалённое 0. Строка с суммой 0 не пишется. Примеры:
- новое пополнение 5 000: +5 000; новый перевод 6 770 из «на жизнь»: −6 770; новая повседневная трата 1 000 с любой датой: −1 000;
- правка пополнения 5 000 → 6 000: +1 000; правка траты 2 000 → 2 500: −500; смена одной даты: строки нет;
- удаление пополнения 5 000: −5 000; удаление траты 2 000: +2 000 - в каком бы периоде они ни были внесены;
- пополнение 5 000, исправленное в перевод между конвертами: −5 000; повседневная трата 1 250, исправленная в трату из конверта: +1 250, и обратно;
- перевод между конвертами и трата из конверта: строк нет.

Почему «минус уже записанное», а не «минус влияние старой версии»: для всего, что вносилось после первой раскладки, это одно и то же. Разница только у трат, внесённых до первой раскладки: строк у них нет (периода ещё не было), поэтому их удаление «на жизнь» не меняет (сценарий «Трата до первой раскладки»).

Внутри одного периода журнал даёт то же, что раньше: внёс трату 1 250 и удалил - 0. Трата и перевод задним числом попадают в текущий период, потому что строка пишется в момент внесения, а не по дате.

Альтернативы:
- По дате (`date >= periodStart`), как траты сейчас. Отклонено: трата и пополнение задним числом не попали бы в текущее «на жизнь».
- Ссылка на период в самом переводе или трате. Отклонено: правка старой траты должна менять текущее «на жизнь» на разницу, а удаление - возвращать сумму; по ссылке из строки, которой уже нет, этого не посчитать.
- Мягкое удаление с пометкой «удалено в таком-то периоде». Отклонено: покрывает удаление, но не правку на разницу; журнал покрывает оба случая одним правилом.

### 3. Расчёты в `src/domain/`

- `envelope.ts`: `envelopeBalance` получает ещё `transferredIn` и `transferredOut`: начальный + раскладки + пришло переводами − траты − ушло переводами. Тест на сценарий «Переводы в конверт и из конверта» (10 000 + 3 000 + 1 500 − 2 000 − 4 000 = 8 500).
- `daily.ts`:
  - `dailyMove({ effect, journaled })` = `effect − journaled`: сумма новой строки журнала.
  - `expenseDailyEffect(expense | null)`: −сумма у повседневной траты, 0 у траты из конверта и у удалённой.
  - `periodBudget({ toDaily, transferMoves })` и `periodSpent(expenseMoves)`; `dailySummary` получает уже посчитанные бюджет и потрачено и не меняется.
  - Тесты бюджета: 86 250 + 5 000 − 2 000 = 89 250; 91 250 («Пополнение задним числом»); 120 225, 114 225, 119 225 (правка, удаление, смена даты старого пополнения); 91 250 / 71 770 и 79 480 / 60 000 (пополнение и обратный перевод).
  - Тесты «потрачено»: 19 225 + 1 000 = 20 225 и осталось 99 000 («Трата задним числом»); 17 225 и 102 000 («Удаление старой траты»); 19 725 и 99 500 («Правка старой траты»); смена даты - без изменений.
  - Подсказка «На жизнь останется» = сейчас осталось + `dailyMove` черновика: новая трата 1 250 при 66 770 → 65 520; правка 1 250 → 1 500 при 65 520 → 65 270.
- Новый `transfer.ts`:
  - `TransferSide = { kind: "daily" } | { kind: "envelope"; envelopeId: string } | { kind: "deleted" }`. `deleted` - удалённый конверт: бывает только у сохранённого перевода.
  - `canTransfer({ amount, from, to, date, today, dailyAvailable, initial })`: сумма > 0; обе стороны выбраны и разные; дата не позже `today`; «на жизнь» только при `dailyAvailable`; `deleted` только на той стороне, где он был у `initial`. Одна функция для кнопки и для проверки на сервере.
  - `signedAmount(transfer, viewpoint)`: для строки истории и для правки - сумма со знаком: «−», если деньги ушли с этой стороны, «+», если пришли. Влияние перевода на «на жизнь» - `signedAmount(transfer, daily)`.
  - `withoutTransfer(balance, viewpoint, initial)` = `balance − signedAmount(initial, viewpoint)`: остаток конверта так, будто старого перевода не было.
  - `transferHint`: для конверта-источника остаток без старого перевода − сумма и «хватит ещё на N раз» (та же арифметика, что `expenseHint`); для конверта-получателя остаток без старого перевода + сумма и «хватит на N раз»; для «на жизнь» - сейчас осталось + `dailyMove` черновика; у каждой стороны флаг «минус». У стороны `deleted` подсказки нет. Тесты на сценарии подсказки, включая «Подсказка при правке» (12 600 − 2 000 = 10 600, 6 400 + 2 000 = 8 400) и правку пополнения 5 000 → 6 000 при оставшихся 71 770 (72 770).
- Округлений нет: переводы и траты только складываются и вычитаются.
- Тест «Перевод делает конверт полным»: раскладка демо-данных, где «Подарки» 27 000 и «Подушка» 14 500 - излишек 2 250 уходит в «Технику», она получает 3 150, Miscellaneous 6 550. Это проверка, что раскладка опирается на остаток, а не на начальные данные; код раскладки не меняется.

### 4. Запросы

- `loadWallets`: ещё два агрегата `sum(amount)` из `transfers`: по `to_envelope_id` и по `from_envelope_id`. Их получает `envelopeBalance`. От этого остатки, статусы, «Всего в конвертах», суммы кошельков и раскладка учитывают переводы сами.
- Новый `loadDailySummary(userId, today)`: последний доход, две суммы строк журнала этого дохода (по `source`), `periodBudget`, `periodSpent`, `dailySummary`. Возвращает `null`, пока дохода нет. Им пользуются главная, экран «Траты», форма траты (новая и правка) и форма перевода. `loadDailySpent` и `periodStart` удаляются: «потрачено» больше не считается по дате.
- `loadExpense` и новый `loadTransfer(userId, id)` возвращают ещё `journaled` - сумму строк журнала этой траты или перевода; она нужна подсказке при правке.
- Новый `loadTransfers(userId, { envelopeId } | { daily: true }, limit = 10)`: переводы стороны по `date desc, created_at desc`, с названиями конвертов обеих сторон (`left join` на `envelopes` дважды, с алиасами).
- Все запросы фильтруют по `user_id`.

### 5. Действия

- Общий помощник `recordDailyMove(tx, userId, item, effect)`: берёт последний доход и уже записанное по этой трате или переводу, считает `dailyMove` и пишет строку, если она не 0 и доход есть. Вызывается внутри той же транзакции, что и изменение траты или перевода.
- `saveExpense` и `deleteExpense`: изменение траты и строка журнала - в одной транзакции. Удаление: строка `dailyMove({ effect: 0, journaled })`, потом удаление траты. Остальные проверки не меняются.
- `saveTransfer({ id?, amount, from, to, date })`: без `id` - новый перевод, с `id` - правка своего перевода. Проверки: `isIsoDate(date)` и `canTransfer` с `today = todayIso()`; каждый конверт стороны принадлежит пользователю, как в `saveExpense`; `deleted` принимается, только если у сохранённого перевода эта сторона - удалённый конверт (тогда ссылка остаётся пустой); сторона «на жизнь» - только при разложенном доходе. Перевод и строка журнала - в одной транзакции. Ошибки: «Выберите, откуда и куда», «Конверт не найден», «Перевод не найден», «Сначала разложите деньги», «Дата не может быть позже сегодняшней».
- `deleteTransfer(id)`: в одной транзакции строка журнала и удаление перевода по `id` и `user_id`; «Перевод не найден», если строки нет.
- Все вызывают `refresh()`, как остальные действия.

### 6. Миграция с заполнением журнала

Миграция создаёт `transfers`, `daily_moves` и тип `daily_move_source` (DDL - `drizzle-kit generate`), а потом заполняет журнал по уже внесённым повседневным тратам: отдельный SQL в той же миграции (`drizzle-kit generate --custom` для второго файла или дописать в сгенерированный). Каждой трате без конверта - строка `source = 'expense'`, `amount = −сумма`, `income_id` = доход того же пользователя с наибольшей датой не позже даты траты (при равных датах - внесённый последним, как в `loadLatestIncome`). Траты раньше первого дохода строк не получают.

Так «потрачено» текущего периода после миграции равно старой формуле - тратам без конверта с даты последнего дохода, а у старых трат есть строки в их периодах, и их удаление вернёт деньги в текущее «на жизнь».

### 7. Форма перевода: `/transfers/new` и `/transfers/[id]`

- Одна клиентская форма `transfer-form.tsx` с `initial` для правки, как `ExpenseForm`.
- Параметры: `from` - экран, куда вернуться (через `safeBackHref`, как у трат); `to=daily` - «Куда» сразу «На жизнь» (только для нового). Без `from` - на главную.
- Новый: `CloseHeader` «Перевод» с крестиком. Правка: `ScreenHeader` «Перевод», назад - на `from`. Чужой или несуществующий перевод - «не найдено».
- Сумма крупно, как в форме траты (`MoneyInput size="xl"`, автофокус только у нового).
- «Откуда» и «Куда» - по строке: выбранная сторона кнопкой-чипом и её остаток, либо «Выбрать». Нажатие раскрывает список: первым чип «На жизнь» (если доход разложен), под ним кошельки в своём порядке с чипами конвертов по приоритету - та же разметка, что «Все конверты» в форме траты. Выбор закрывает список. У нового перевода сразу раскрыт список «Откуда», если «Откуда» ещё не выбрано. У перевода с удалённым конвертом на этой стороне выбран чип «Удалённый конверт», в списке он стоит первым; выбрав другую сторону, можно вернуть его, пока форма не сохранена.
- «Дата» - строка в карточке, как в форме траты: `type="date"`, `max = today`, по умолчанию сегодня, у правки - дата перевода.
- Чип `Chip` выносится из `expense-form.tsx` в `src/components/chip.tsx` и используется обеими формами.
- Подсказка под выбором: до двух строк, по одной на сторону, каждая своим цветом (`accent-soft` или `warn-soft`), тексты из спеки. При правке - по `withoutTransfer` и `journaled`.
- Кнопка - основная (`primaryButtonClass`): «Перевести» у нового, «Сохранить» у правки; «Перевожу…» / «Сохраняю…» на время сохранения. После успеха - `router.push(back)` и `router.refresh()`, как у траты.
- У правки - `ConfirmButton` «Удалить перевод», окно «Удалить перевод?» и «4 200 ₽ вернутся в конверт «Маникюр»» или «… вернутся на жизнь». Если источник - удалённый конверт: «… уйдут из конверта «Маникюр»», потому что вернуться им некуда.

### 8. Форма траты

- Страница правки траты передаёт в форму «сейчас осталось на жизнь» (`loadDailySummary`) и `journaled` траты; новая трата - только остаток, `journaled = 0`.
- Подсказка «На жизнь останется» в режиме «Повседневное» = осталось + `dailyMove` черновика, и у новой траты, и у правки. Сейчас у новой траты то же число (осталось − сумма), у правки подсказка появляется впервые.

### 9. Кнопки и блоки «Переводы»

- Экран кошелька: под двумя плитками кнопка «Перевести» на всю ширину, вторичная: фон `surface`, текст `accent`, скругление 14 px. Ведёт на `/transfers/new?from=/wallets/<id>`.
- Карточка «Осталось на жизнь» на экране «Траты»: справа в строке с суммой чип «Пополнить» (`accent-strong`, белый текст, как чипы на акцентной карточке главной). Ведёт на `/transfers/new?to=daily&from=/daily`. Без раскладки карточки нет, значит и чипа нет.
- Блок «Переводы» на экране конверта - после «Последние траты»; на экране «Траты» - после «Последние». Строка как у трат: слева подпись и дата (`formatRelativeDay`), справа сумма со знаком. Подписи: «В конверт «X»», «Из конверта «X»», «На жизнь», «Из денег на жизнь», «В удалённый конверт», «Из удалённого конверта». Нажатие - `/transfers/<id>?from=<этот экран>`.
- Пояснение к карточке «Осталось на жизнь» больше не стоит отдельным абзацем под ней. В правом верхнем углу зелёной карточки, в строке «Осталось на жизнь», - значок «i» в кружке: линейная иконка `InfoIcon` в `src/components/icons.tsx`, белая, зона нажатия 44×44 px, подпись для экранного диктора «Пояснение». Чип «Пополнить» остаётся справа в строке с суммой, ниже значка.
- Нажатие на «i» открывает плашку под значком: текст «Это всё, что осталось от зарплаты после конвертов, с пополнениями из конвертов. Траты из конвертов эту сумму не уменьшают, но видны в категориях» и крестик (`CloseIcon`, подпись «Закрыть»). Плашка - фон `surface`, текст `ink`, скругление 16 px, тень как у окна подтверждения.
- Плашка закрывается крестиком, любым нажатием на экране, в том числе на саму плашку, клавишей Esc и сама через 8 секунд. Нажатие мимо плашки не перехватывается: то, на что нажали, срабатывает как обычно. Нажатие на «i» при открытой плашке её закрывает.
- Компонент - `Popover` из shadcn/ui в `src/components/ui/popover.tsx` на уже установленном пакете `radix-ui`, новой библиотеки нет. Закрытие по нажатию мимо и по Esc он делает сам; таймер 8 секунд и закрытие нажатием на плашку - свои, в клиентском компоненте карточки. Цвета и скругления - токенами, не по умолчанию из shadcn.

### 10. Решено без отдельного вопроса

Это следует из ответов или из того, как уже устроены траты; при проверке можно поменять:

- Будущую дату перевода выбрать нельзя, как у трат.
- До первой раскладки «На жизнь» не участвует в переводах: периода и бюджета ещё нет.
- Повседневная трата, внесённая до первой раскладки, в «потрачено» не входит, её удаление «на жизнь» не меняет. Если такую трату исправить после раскладки, она начнёт учитываться с новой суммой целиком.
- Если удалены старые траты, «потрачено» может стать меньше трат с даты зарплаты и даже отрицательным: показывается как есть, со знаком «−», полоска пустая.
- Переводы удалённого конверта остаются у второй стороны, подпись «удалённый конверт».
- Переводы в историю на главной и экране кошелька не выводятся.
- Подписи строк истории и тексты подсказок - как в спеке `transfers`.
- Плашка с пояснением закрывается сама через 8 секунд: столько нужно, чтобы спокойно прочитать два предложения. Esc тоже закрывает, нажатие мимо плашки не перехватывается.

## Risks / Trade-offs

- [«Потрачено» за период больше не совпадает с тратами по датам: трата от 12 ноября видна в списке среди прошлых, а входит в текущее «потрачено»] → Так решено: всё, что делается с тратами, меняет «потрачено». Сценарии «Трата задним числом», «Удаление старой траты».
- [Заполнение журнала в миграции ошибётся, и «Осталось на жизнь» изменится после выкатки] → На локальной базе записать «Осталось на жизнь» и «потрачено» до миграции и сравнить после; SQL-проверка в задачах: для каждого пользователя старая формула равна сумме строк журнала-трат последнего дохода.
- [Журнал разойдётся с тратами и переводами, если изменение сохранится без своей строки или наоборот] → Изменение и строка журнала пишутся в одной транзакции; траты и переводы меняются только действиями из решения 5 (поиск по `insert(expenses)`, `update(expenses)`, `delete(expenses)` в задачах); доменные тесты `dailyMove` на все случаи; e2e проверяют, что после правок и удаления «Осталось на жизнь» возвращается к исходному.
- [Пополнение прошлого периода «пропадает» с новым доходом] → Так решено: с новым доходом начинается новый период. Конверт деньги не возвращает; сценарий «Новый доход начинает новый период».
- [Запрос, который считает остаток конверта мимо `loadWallets`, не увидит переводов] → Остаток считается только в `loadWallets`; в задачах - поиск по `envelopeBalance` и `expenses.envelopeId` в `queries.ts` и `actions.ts`.
- [Удаление или уменьшение перевода, у которого источник - удалённый конверт, уменьшает живую сторону] → Окно подтверждения прямо пишет, что деньги уйдут из конверта; при правке это видно в подсказке.
- [e2e меняют общую базу, сценарии компьютера идут после] → Каждый новый e2e-сценарий в конце удаляет свои переводы и траты и проверяет, что суммы вернулись. Ожидания в e2e считаются от сумм на экране до действия, точные числа из сценариев проверяют доменные тесты.

## Migration Plan

1. Миграция создаёт таблицы `transfers` и `daily_moves` с проверками и индексами и заполняет журнал по уже внесённым повседневным тратам (решение 6). Применяется разовым контейнером до старта нового образа, как обычно.
2. Проверка после миграции: «Осталось на жизнь» и «потрачено» те же, что до неё.
3. Откат: старый образ не знает про новые таблицы - не учитывает переводы и снова считает «потрачено» по дате трат. Остатки конвертов и «на жизнь» станут такими, будто переводов не было, а траты задним числом посчитаются по старому правилу. Таблицы можно оставить. Автооткат не делаем (CLAUDE.md).
