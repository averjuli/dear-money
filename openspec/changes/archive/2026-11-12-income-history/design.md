# Design

## Context

- Доход хранится в `incomes` (дата, сумма, вид, `to_envelopes`, `to_daily`, `created_at`), строки его раскладки - в `allocations` (`income_id` с `on delete cascade`, `envelope_id` с `on delete cascade`, `amount`, `kind`, `source_envelope_id`).
- Дата дохода в форме не выбирается: это всегда день внесения (`todayIso()` в `src/app/income/page.tsx`). Порядок доходов по `(date, created_at)` совпадает с порядком по `created_at`.
- Остаток конверта считается на лету: `start_balance + Σ allocations − Σ expenses ± transfers` (`loadWallets` в `src/server/queries.ts`). Удаление или замена строк `allocations` сами меняют остатки.
- «Осталось на жизнь» = `Σ incomes.to_daily + Σ daily_moves.amount` (`loadDailySummary`, `dailyRemaining`). Пока доходов нет, карточки нет.
- Журнал `daily_moves` привязан к доходу через `income_id NOT NULL ... on delete cascade`. Поле только пишется (`recordDailyMove` в `src/server/actions.ts`), нигде не читается. Удаление дохода как есть стёрло бы строки журнала его периода.
- `recordDailyMove` ничего не пишет, пока нет ни одного дохода: так работает «Трата до первой раскладки».
- Раскладку одного дохода считает `planAllocation(wallets, envelopes, amount, skippedWalletIds)` в `src/domain/allocation.ts` от текущих остатков. Галочки (`skippedWalletIds`) сейчас не сохраняются.
- У `expenses`, `transfers`, `envelopes` есть `created_at`; правки трат и переводов меняют сумму и стороны, но не `created_at`.
- Шаблон «список → экран записи → удалить с подтверждением» уже есть у переводов: `TransferList`, `/transfers/[id]?from=...`, `ConfirmButton`, `deleteTransfer`.
- e2e-сценарии идут по одной базе по порядку (`playwright.config.ts`), следующие тесты рассчитывают на уже разложенные доходы и остатки.

## Goals / Non-Goals

**Goals:**
- Править и удалять доход одной транзакцией, пересчитывая этот и все следующие доходы по правилам спеки.
- Пересчёт - чистая функция в `src/domain/` с тестами на числа из сценариев.
- Журнал «на жизнь» не теряется при удалении дохода; уже учтённое продолжает учитываться и при нуле доходов.

**Non-Goals:**
- Правка даты дохода.
- Снимки настроек конвертов на момент дохода: пересчёт берёт текущие настройки.
- Показ до сохранения, как изменится каждый следующий доход: только их число.
- Мягкое удаление и восстановление удалённого дохода.
- Постраничная загрузка экрана «Все доходы».

## Decisions

### 1. Схема: `daily_moves.income_id` необязательная, у дохода запомненные галочки

Одна миграция Drizzle:
- `daily_moves.income_id`: снять `NOT NULL`, внешний ключ пересоздать с `on delete set null`.
- `incomes.skipped_wallet_ids uuid[] not null default '{}'`: кошельки со снятой галочкой. Для уже разложенных доходов - пустой список, то есть «все отмечены», как решено в спеке.

Строки не меняются. Массив без внешнего ключа: удалённый кошелёк просто не найдётся среди текущих и не учитывается.

Альтернативы:
- Перепривязывать строки журнала к предыдущему доходу: при удалении единственного дохода некуда.
- Отдельная таблица `income_skipped_wallets` с внешними ключами: аккуратнее, но лишняя таблица ради списка из 0–5 значений, который читается только целиком.

### 2. Журнал при нуле доходов: уже учтённое продолжает учитываться

Если доходов нет, но у траты или перевода уже есть строки журнала (`journaled ≠ 0`), строка пишется как обычно (`effect − journaled`) с `income_id = null`; если строк нет - как раньше, ничего. Решение - чистая функция в `src/domain/daily.ts`, тесты: новая трата без дохода → 0; удаление учтённой −2 000 → +2 000; правка учтённой на 2 500 → −500.

Альтернатива: журналировать всегда, даже до первой раскладки. Ломает требование «Трата до первой раскладки».

### 3. Пересчёт цепочки доходов - чистая функция `replayIncomes`

В новом `src/domain/income.ts`. Вход:
- текущие кошельки (порядок) и конверты (настройки, `startBalance`, `createdAt`, `walletId`);
- события, меняющие остатки, с моментом внесения: траты из конвертов, переводы (обе стороны), строки раскладки доходов, которые не пересчитываются (более ранних);
- пересчитываемые доходы по порядку: `createdAt`, сумма, `skippedWalletIds`, `toDeleted` (ушло в удалённые конверты, см. решение 4).

Для каждого дохода по порядку:
1. Конверты на момент дохода - те, у кого `createdAt` раньше дохода.
2. Остаток конверта = `startBalance` + события раньше дохода + строки уже пересчитанных доходов этой цепочки.
3. `planAllocation(кошельки, конверты, amount − toDeleted, skipped)`.
4. `toEnvelopes = toDeleted + plan.toEnvelopes`, `toDaily = plan.toDaily`, строки - `plan.lines`.

Выход - новые строки, `toEnvelopes` и `toDaily` для каждого дохода. «Раньше» сравнивается по `createdAt`; функция получает уже упорядоченные данные и ничего не знает о базе. Тесты - сценарии «Правка делает конверт неполным», «Удаление делает конверт неполным», «Трата между доходами», «Конверт создан позже дохода», «Запомненные галочки», «Удалённый конверт при пересчёте».

Альтернатива: пересчитывать через снятие «дельт» от старых строк к новым. Трудно доказать правильность при каскаде излишков; полный пересчёт хвоста проще и при 2–3 доходах в месяц дёшев.

### 4. Деньги удалённых конвертов: `toDeleted = to_envelopes − Σ живых строк`

Строки раскладки удалённого конверта исчезают каскадом, поэтому сумма, ушедшая в удалённые конверты, восстанавливается как разница. Перед пересчётом она считается для каждого дохода цепочки и сохраняется в новом `to_envelopes`. Валидация правки: сумма не меньше `toDeleted` этого дохода, иначе `fail("Не меньше X ₽: столько ушло в удалённые конверты")`.

### 5. Серверные действия - одна транзакция с блокировкой

- `allocateIncome`: дополнительно сохраняет `skipped_wallet_ids` (только свои кошельки, как сейчас фильтруются).
- `updateIncome({ id, amount, kind, skippedWalletIds })`: `requireUserId`, `isUuid`, сумма > 0, вид из списка; в транзакции `select ... for update` всех доходов пользователя (две правки одновременно не перемешаются), найти свой доход, иначе `fail("Доход не найден")`; посчитать `toDeleted`, проверить сумму; обновить сумму, вид, галочки; загрузить вход для `replayIncomes` с этого дохода включительно; удалить строки `allocations` этих доходов и вставить новые, обновить `to_envelopes`/`to_daily`. `pay_days` не трогать.
- `deleteIncome(id)`: та же блокировка и проверка владельца; удалить доход (строки уходят каскадом, журнал получает `null`); пересчитать доходы после него так же.
- Оба вызывают `refresh()`.

Вход для `replayIncomes` собирает новая функция в `src/server/queries.ts`, все запросы с фильтром `user_id`, внутри той же транзакции.

### 6. Предпросмотр правки на клиенте

Сервер передаёт форме правки кошельки и конверты «на момент дохода» (решение 3, шаги 1–2, без строк самого дохода), `toDeleted` и число следующих доходов. `IncomeForm` в режиме правки считает предпросмотр тем же `planAllocation` от `amount − toDeleted` и прибавляет `toDeleted` к «В конверты»; поля чисел аванса и зарплаты скрыты, кнопка «Сохранить». Сервер всё равно считает заново и предпросмотру не доверяет, как сейчас в `allocateIncome`.

### 7. Экранные функции домена

- `incomeBreakdown(lines, wallets, envelopes, toEnvelopes)`: кошельки по `position`, конверты по приоритету, взнос и излишек, пропуск нулевых, `toDeleted`.
- `incomeDeletionEffect(income, lines)`: `{ fromEnvelopes, fromDaily }` для окна подтверждения; число следующих доходов приходит с сервера.

### 8. Маршруты и экраны

- `/income` - форма + блок «История» (`loadIncomes(userId, 11)`: 10 строк и признак «есть ещё»).
- `/income/all` - «Все доходы»; статический сегмент имеет приоритет над `[id]`.
- `/income/[id]` - экран дохода, `not-found` как у конвертов; кнопки «Изменить» и «Удалить доход» (`ConfirmButton`).
- `/income/[id]/edit` - форма правки.
- `?from=` с белым списком `/income`, `/income/all`; «Сохранить» ведёт на `/income/[id]` с тем же `from`.
- Меню разделов на новых экранах не показывается: `menuSection` сверяет точный путь.
- Подписи видов дохода - общие в `src/lib/text.ts`.

## Risks / Trade-offs

- [Пересчёт с текущими настройками меняет поздние доходы неожиданно, если цены или приоритеты успели поменяться] → решено в спеке; форма и окно подтверждения показывают, сколько раскладок пересчитается.
- [Неверный момент «до дохода» из-за часовых поясов] → сравниваются только `created_at` (timestamp with time zone), дата не участвует.
- [Каскадное удаление конверта уже стёрло его строки, `toDeleted` считается разницей] → если `to_envelopes` у старых доходов почему-то меньше суммы строк, `toDeleted` отрицателен: функция берёт `max(0, …)` и тест на это.
- [Удаление необратимо] → подтверждение на экране; бэкап базы перед каждой выкаткой уже есть.
- [e2e идут по общей базе] → тесты правки и удаления раскладывают в конце цепочки два своих небольших дохода «Другое», правят и удаляют их и в конце удаляют оба, проверяя, что остатки вернулись к значениям до них.
- [Ссылка `from` подставляется из адреса] → белый список путей.

## Migration Plan

1. Новая миграция Drizzle (`drizzle/0005_*.sql`): `daily_moves.income_id drop not null` + FK `on delete set null`; `incomes.skipped_wallet_ids uuid[] not null default '{}'`. Существующие строки по смыслу не меняются; SQL приложить к PR.
2. Выкатка обычным путём: бэкап → миграции → новый образ → `/health`.
3. Откат образа на предыдущий безопасен: старый код не читает новую колонку, всегда заполняет `income_id` и не правит и не удаляет доходы. Доходы, исправленные новой версией, старая показывает с новыми суммами.
