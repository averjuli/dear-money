# Dear Money

Личный планировщик накоплений по методу конвертов. Откладываю деньги под редкие расходы, вижу, на сколько раз хватит каждого конверта, а остаток зарплаты идёт на повседневную жизнь.

- Идея и ограничения: `specs/01-продуктовая-идея.md`
- Экраны и дизайн: `specs/02-экраны-и-дизайн.md`, макеты в `design/`
- Требования фич: `openspec/specs/`
- Правила для Claude Code: `CLAUDE.md`

## Что в репозитории сейчас

Только спеки, макеты и стартовые данные. Кода ещё нет: его пишет Claude Code по плану ниже.

| Папка или файл | Что внутри |
|---|---|
| `specs/` | Продуктовая идея, экраны, дизайн-токены, открытые вопросы |
| `openspec/specs/` | Требования по фичам со сценариями и числами для тестов |
| `design/` | Макеты 7 экранов и наброски маскота Копи |
| `data/demo-seed.json` | Демо-данные: названия кошельков и конвертов как у меня, суммы выдуманные. Можно в git |
| `data/my.local.json` | Мои настоящие данные. Не в git |
| `.env.example` | Какие настройки нужны, без значений |

## План

Делаем по одной фиче. Каждая: ветка → требования из `openspec/specs/` → план → код с тестами → PR.

| # | Фича | Спека | Готово, когда |
|---|---|---|---|

| 5 | База и загрузка начальных данных | `envelopes` | Мои кошельки из `data/my.local.json` в базе |
| 6 | Главная и кошелёк | `envelopes` | Экраны 1, 5, 6 как в макете, перетаскивание работает |
| 7 | Пришли деньги | `income-allocation` | Экран 3, раскладка сохраняется |

Пункты 3 и 4 самые важные: это логика, ради которой приложение и делается. Её проверяем тестами до того, как рисовать экраны.

## Запуск на компьютере

Нужны: Node.js, pnpm, Docker.

```
cp .env.example .env               # заполнить строки базы (POSTGRES_*, DATABASE_URL)
docker compose up -d db            # Postgres на 127.0.0.1, порт из POSTGRES_PORT
pnpm install
pnpm db:migrate                    # таблицы в базе
pnpm auth:setup                    # спросит логин и пароль, запишет в .env хеш и секрет
pnpm db:seed data/sample-seed.json # тестовые данные: 5 кошельков, трат нет
pnpm build && pnpm start           # http://localhost:3000
```

- `pnpm auth:setup` запускать в обычном окне терминала: пароль вводится скрыто и в `.env` попадает только его хеш
- Свои данные: `pnpm db:seed data/my.local.json`. Повторная загрузка не создаёт дублей и не перезаписывает то, что изменено в приложении
- `data/demo-seed.json` - демо-данные для тестов; `data/sample-seed.json` - тестовые данные для ручной проверки, на них сходятся числа из критериев успеха. Суммы в обоих файлах выдуманные

## Проверки

```
pnpm test        # логика расчётов и вход (Vitest)
pnpm test:e2e    # главный сценарий в браузере на отдельной базе dear_money_e2e (Playwright)
pnpm lint
pnpm typecheck
pnpm format:check
```

Перед `pnpm test:e2e` нужна сборка `pnpm build` и запущенный Postgres. Первый раз: `pnpm exec playwright install chromium`.

## Выкатка

Тот же VPS, что у CRM и лендинга, свой поддомен и своя база в отдельном контейнере Postgres. Выкатка автоматическая: чтобы выкатить новую версию, достаточно влить PR в main.

Что делаю сама: записи DNS, первая настройка сервера с `sudo`, строки в `.env` на сервере, ручной откат, восстановление базы из бэкапа.

### Как это работает

1. На каждый PR GitHub Actions проверяет код (lint, формат, типы, Vitest, Playwright) и пробно собирает образ: `.github/workflows/ci.yml`
2. После merge в main те же проверки идут ещё раз. Потом собирается образ с тегом SHA коммита и уходит в GHCR (`ghcr.io/averjuli/dear-money`): `.github/workflows/deploy.yml`
3. GitHub Actions заходит на сервер по ключу деплоя и запускает `dear-money-deploy deploy <SHA>` (скрипт `deploy/dear-money-deploy.sh`). Первым шагом он делает резервную копию базы, потом скачивает новый образ, применяет миграции в разовом контейнере из него, запускает новый образ и проверяет `https://app.dearmoney.space/health`
4. Не получилась резервная копия или упали миграции: новый образ не стартует, работает прежний. Не прошла проверка `/health`: выкатка красная во вкладке Actions. Сам ничего не откатывается, откат только вручную
5. На сервере остаются два образа, текущий и предыдущий, и 10 последних резервных копий базы

Резервная копия называется `dear-money-20261110-201500-<версия>.sql.gz`: дата и время копии и версия приложения (SHA коммита), которая тогда работала. У копии из выкатки это версия, которая стояла до выкатки.

Ход выкатки виден во вкладке Actions на GitHub, workflow «Deploy».

### На сервере

| Что | Где |
|---|---|
| Приложение и его база | `/opt/dear-money`, compose-проект `dear-money` |
| Настройки и пароли | `/opt/dear-money/.env`, права 600, читает только root |
| Приложение слушает | `127.0.0.1:3001`, снаружи через nginx |
| Резервные копии базы | `/var/backups/dear-money` |
| Логи контейнеров | не больше 3 файлов по 10 МБ |

Команды, на сервере под `crmapp`:

```
sudo dear-money-deploy status     # что запущено, текущая и предыдущая версии, /health
sudo dear-money-deploy logs       # последние 200 строк лога приложения
sudo dear-money-deploy rollback   # вернуть предыдущую версию, только вручную
sudo dear-money-deploy backup     # резервная копия базы
sudo dear-money-deploy restore    # список резервных копий; с именем файла - восстановить базу, см. ниже
sudo dear-money-deploy seed       # тестовые данные из data/sample-seed.json, повтор не создаёт дублей
```

Секреты GitHub для выкатки: `DEPLOY_HOST` (адрес сервера), `DEPLOY_SSH_KEY` (ключ деплоя), `DEPLOY_KNOWN_HOSTS` (отпечатки сервера). Публичная часть ключа лежит у `crmapp` в `~/.ssh/authorized_keys` с подписью `github-actions-deploy dear-money`, и этот ключ может запускать только `dear-money-deploy`.

### Восстановление базы из бэкапа

Только вручную, в терминале на сервере: без терминала команда не запустится, поэтому GitHub Actions её запустить не может. Восстанавливает в пустую базу: удаляет базу Dear Money, создаёт заново и загружает в неё резервную копию. Базы и контейнеры CRM и лендинга не трогает.

1. Зайти на сервер: `ssh crmapp@<IP сервера>`
2. Посмотреть резервные копии, новые сверху: `sudo dear-money-deploy restore`
3. Запустить с нужным файлом: `sudo dear-money-deploy restore dear-money-20261110-201500-<версия>.sql.gz`. Можно имя из списка, можно полный путь
4. Скрипт проверит, что файл целый и это резервная копия базы, и покажет: какой файл, какую базу заменит, какая версия приложения работает. Проверить и ввести `yes`. Любой другой ответ - выход, ничего не меняется
5. Дальше скрипт сам: сохраняет копию текущей базы (`...-before-restore.sql.gz`), останавливает приложение, восстанавливает базу, запускает ту же версию приложения и проверяет `/health`. Пока идёт восстановление, на app.dearmoney.space страница «недоступно»

Если что-то пошло не так:

- **Версия в имени копии не та, что работает сейчас** - скрипт предупредит перед `yes`. Restore версию приложения не меняет и миграции не применяет. Типичный случай - неудачная выкатка испортила данные: сначала `sudo dear-money-deploy rollback`, потом restore копии, снятой перед этой выкаткой. Тогда версии совпадут
- **Упала загрузка** - база остаётся пустой, приложение остановлено. Скрипт напишет команду, которая вернёт копию `before-restore`, то есть базу как была до восстановления. Сам он ничего не возвращает
- **Не прошла проверка `/health`** - база уже восстановлена. Смотреть `sudo dear-money-deploy logs`

Restore не удаляет резервные копии. Копия `before-restore` лежит вместе с остальными и считается в 10 последних.

### `.env` на сервере

`/opt/dear-money/.env`, правится через `sudo nano /opt/dear-money/.env`:

```
POSTGRES_USER=dear_money
POSTGRES_DB=dear_money
POSTGRES_PASSWORD=
AUTH_USERNAME=
AUTH_PASSWORD_HASH=
AUTH_SECRET=
```

- `POSTGRES_PASSWORD` - результат `openssl rand -hex 24`. Только буквы и цифры: пароль идёт в строку подключения к базе
- `AUTH_USERNAME` и `AUTH_PASSWORD_HASH` - как в `.env` на компьютере, тогда логин и пароль те же
- `AUTH_SECRET` - результат `openssl rand -hex 32`, свой для сервера
- `APP_TIME_ZONE` необязателен, по умолчанию `Europe/Moscow`

### Адреса и сертификат

- `dearmoney.space` - главная (потом лендинг), заглушка из `deploy/stub/`. `app.dearmoney.space` - приложение: nginx передаёт запросы контейнеру, а пока приложение не запущено, показывает `deploy/unavailable.html`.
- Один сертификат Let's Encrypt на оба адреса, имя `dearmoney.space`. Продлевается сам: на сервере общий `certbot.timer` раз в полдня проверяет все сертификаты, после продления nginx перезагружается хуком из `/etc/letsencrypt/renewal-hooks/deploy`.
- http перенаправляется на https. Порты контейнеров открываем только на `127.0.0.1`, наружу ходим через nginx.

### Первая настройка сервера

Делается один раз. Нужен вход как `crmapp` и пароль для `sudo`.

```
scp -r deploy crmapp@<IP сервера>:dear-money-setup
ssh crmapp@<IP сервера>
sudo bash dear-money-setup/setup-nginx-tls.sh <почта для писем от Let's Encrypt>
```

Скрипт только добавляет своё: сайты nginx `dearmoney-http` и `dearmoney-https`, папки `/var/www/dearmoney.space` и `/var/www/app.dearmoney.space`, сертификат. Чужие сайты, ключи и контейнеры не трогает, Docker только проверяет. Если nginx не принял конфиг, скрипт откатывает свои файлы. Запускать повторно можно: готовые страницы и https-сайт он не перезаписывает.

Почта в репозиторий не попадает: её передаём аргументом.

Потом, тоже один раз, автовыкатка:

```
scp -r deploy crmapp@<IP сервера>:dear-money-setup
ssh crmapp@<IP сервера>
sudo bash dear-money-setup/install-on-server.sh
sudo nano /opt/dear-money/.env     # строки из раздела «.env на сервере»
```

Скрипт создаёт `/opt/dear-money` с пустым `.env` и команду `dear-money-deploy`, разрешает `crmapp` запускать её через `sudo` без пароля и переключает `app.dearmoney.space` с заглушки на приложение. Чужое не трогает. Если nginx не принял конфиг, скрипт возвращает прежний. Запускать повторно можно: готовый `.env` он не перезаписывает.
